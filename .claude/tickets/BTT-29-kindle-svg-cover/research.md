# REQ-0008 research: Croatian EPUBs look fixed-layout on Kindle

## Question
Why do the Book Translator hr EPUBs open on Kindle like a fixed-layout book (cover, dark bar, title page, body running off both edges, progress 7% / 14% / 21% per page) while the English Scriptorium EPUBs reflow fine, and what is the smallest fix?

## Answer
- Only one structural difference exists between English source and hr output beyond translated text and `lang`: the hr files got an **SVG cover** injected by Book Translator's `cover: 'title'` option. It adds `translated-cover.svg` (manifest item `properties="cover-image"`, `image/svg+xml`) and a new first spine page `translated-cover.xhtml` that holds only that SVG. **Confirmed** by diff (all three hr books have it; English source has none).
- No `rendition:*`, no viewport meta, no fixed widths, no `pre-paginated`, mimetype is first/STORED in both, XHTML head/doctype/xmlns identical, CSS byte-identical, epubcheck gives identical results for both (one pre-existing OPF-096 error on `nav linear="no"`, in English too). So the "fixed layout" is Amazon's converter reaction, not a declared layout. **Confirmed.**
- Most likely cause: an SVG as the declared cover image plus a spine page that is just an SVG image. Kindle/KDP expects cover images as JPEG/PNG, and treats SVG-only pages as image pages. Mechanism on the Kindle side is **inferred** (I could not run Kindle Previewer or search the web in this session). Confidence: high that the SVG cover is the only candidate (nothing else differs); medium (about 70%) that it is the trigger; the exact Kindle behaviour is unverified.
- Not the cause (evidence): dc:language `hr` (the same hr value is in the OPF and every XHTML in books that also differ only by cover; nothing else differs, and Amazon does accept Croatian as a book language; unverified on the Send to Kindle page), rendition properties (none), mimetype (identical).
- Smallest fix: stop adding an SVG cover. Re-export the hr books without `--cover title` (the source cover is the text title page `cover.xhtml`, which is fine), and in the writer never emit an SVG as `cover-image` (see "Code location").

## Path through the code
- Book Translator project `sourcePath` = Scriptorium's `books/<slug>/out/<slug>.epub` (`project.json` of all three; confirmed for the tide-table, what-fate, one-way-street projects). The EPUB adapter edits that source in place and copies other entries byte for byte (`C:/projects/Personal/book-translator/src/engine/formats/epub.ts` header comment, `write()` ~line 305 onward).
- Export option `cover: 'title'` is set by the CLI (`src/engine/cli.ts:197`), dispatcher (`src/engine/dispatcher.ts:732`) and MCP tool `export_project` (`src/engine/mcp/server.ts:271`); service passes it to the adapter (`src/engine/service.ts:546`). Default is `source`. Which entry point produced these three files is not recorded (log.md has no cover note), but the SVG proves `cover: 'title'` was used. **Confirmed** (artifacts), caller **inferred**.
- In `write()`, with `opts.cover === 'title'`: `titleCoverSvg()` (`src/engine/publish/cover.ts`, 1200x1800 SVG with `<text>`, Georgia font, no raster) is added as `translated-cover.svg`; every existing cover-image property is removed; a manifest item `translated-cover` `image/svg+xml` gets `properties="cover-image"`; `<meta name="cover">` is repointed if present. When the source has no image cover (`newCover.used === false`, which is the case for Scriptorium books without a generated PNG), a page `translated-cover.xhtml` is built with `xhtmlPage(...)` and inserted as the first `itemref` (`epub.ts` the `if (!newCover.used && spine)` block). That page has `<img src="translated-cover.svg" style="max-width:100%;max-height:100%"/>`, no stylesheet (the `<link>` is stripped by `.replace(/<link[^>]*>\n?/, '')`), no viewport.
- Scriptorium's own writer: `C:/projects/Personal/scriptorium/src/engine/publish/epub.ts:122-127,214` uses a PNG cover with `cover-image` only when a PNG exists; otherwise a text title page and no cover-image. So English EPUBs never contain an SVG cover or an image-only first page. **Confirmed.**

## What the plan needs
1. Decide the fix (options):
   - A (data only, no code): re-export the three books with `cover` omitted (`source`). For these Scriptorium books the source cover is the text `cover.xhtml`, so the result equals the English structure plus Croatian text. Re-send to Kindle.
   - B (code, recommended on top of A): in `book-translator/src/engine/formats/epub.ts` `write()`, do not create an SVG cover for `cover: 'title'`. Either (i) when the source has no cover image (`!newCover.used`), skip the cover entirely since `cover.xhtml` already is a title page, or (ii) render the title cover to PNG/JPEG (need a rasteriser, new dependency, more work). Never put `image/svg+xml` in `properties="cover-image"`; never add an image-only page as first spine item without CSS.
   - C: if a raster cover is wanted for Scriptorium books, let Scriptorium produce `coverPng` (already supported, `scriptorium/src/engine/publish/epub.ts:35,122`).
2. Tests: look for existing cover tests in `book-translator/tests` (not searched in this session) and add one asserting that `cover: 'title'` on a source without a cover image yields no `image/svg+xml` `cover-image` item and no extra spine item.
3. Verification without a Kindle: unzip the output, assert no `image/svg+xml` with `cover-image` and no `translated-cover` in OPF; run epubcheck (jar in the temp folder); ideally open in Kindle Previewer 3 (free, Amazon) or Calibre `ebook-convert x.epub x.azw3` (both free, not installed here) and view the output. With a Kindle: send `tide-table.hr.nocover.epub` first. If it reflows, the SVG cover is confirmed. If it does not, next suspects in order: `dc:language` hr / Send to Kindle language list, then a USB copy test (USB .epub is not read by Kindle natively; Send to Kindle converts it, so sideloading an EPUB is not itself a valid path, which tells which route the user used).

## Risks
- Mechanism unproven: if the no-cover variant still shows fixed layout, the cause is elsewhere (language, or the Kindle model/firmware KFX behaviour with SVG `ornament.svg` + `<img>` in chapters). The English books contain the same ornament SVG and work, so the ornament is unlikely.
- `cover: 'title'` is a documented option in three entry points; changing its behaviour affects other users of Book Translator who rely on a replaced cover for sources with an image cover (EPUB 3 sources with a raster cover, where the SVG replaces a JPEG). Even there SVG as cover is risky on Kindle.
- Already-sent copies on the Kindle library and in Amazon's cloud keep the bad conversion; re-sent books with the same title and author may need the old one deleted.
